# 健診分析・保健指導計画作成支援AIエージェント 事前PoC計画書

作成日：2026年10月14日（日本時間）／版：1.0  
標準期間：6週間・30人日（1人、1日6時間の実作業を仮定）  
最小構成：4週間・20人日／拡張上限：8週間・40人日  
関連資料：[AIエージェント設計書](01_ai_agent_design.md)

## 1. 目的と到達点

**本番PoCの提案前に、Gemma 4 31Bを使った健診分析・保健指導計画の下書き支援が、小さな構成で実装できるかを検証し、営業が説明・実演できる証拠を得る。**

完成物は、動作するデモ、固定評価データと評価報告、3症例の営業デモ台本、営業説明資料、本番PoCへの移行条件とする。本計画書に記載した数値は目標・見積もりであり、検証済みの成果ではない。

| 検証したいこと | 得たい証拠 | 今回は結論を出さないこと |
|---|---|---|
| 過去数回の数値を正しく比較できるか | 計算・欠測処理・条件分岐のテスト結果 | 疾患の診断精度・発症予測性能 |
| 根拠を追える計画案を作れるか | 事実・引用・未確認事項の採点結果 | 実際の指導による健康改善 |
| 注意すべきケースを確認に回せるか | 保留・警告の成功と失敗の内訳 | 未見の全症例に対する安全保証 |
| 担当者の準備作業に役立つか | 模擬作業時間・修正量、任意の保健師評価 | 現場全体での人員削減・費用削減 |
| 顧客の導入検討に使えるか | 再現可能なデモ、構成・制約・費用の説明 | 本番運用可能性の確定 |

## 2. 体制と実行条件

### 2.1 1人で成立する基準線

作業者1人が、要件整理・Python実装・データ作成・評価・デモ作成を担当する。Python、Webの簡易UI、LLM推論環境の基本操作を経験している前提とする。GPU環境を新規調達し続ける期間や、契約・稟議の待ち時間は30人日に含まない。兼務で週15時間なら標準180時間に約12週間かかるため、1〜2か月という条件を満たすには稼働確保または4週間版への縮小が必要である。

開発者自身が保健師でない場合でも、形式・数値・ルール一致・引用所在・停止動作の技術検証は進められる。臨床的な妥当性は「未評価」とする。作業者が有資格者でも自己評価には偏りが残る。

保健師等による**外部レビュー4〜6時間は推奨オプション**であり、必須の開発要員には含めない。確保できなければ、技術デモと営業資料の作成は完了させ、「専門家評価済み」「実務時間を削減した」とは説明しない。本番PoCに進む判断時には、医療・保健指導の責任者による評価を別途必要とする。

### 2.2 開始時に固定する事項

| 項目 | 初期案 | 未確定時の扱い |
|---|---|---|
| 対象顧客 | 企業・健保・保健指導事業者 | 面談前準備の共通業務に絞る |
| 対象者 | 主に40〜74歳の成人 | 範囲外は計画生成を保留する検証対象 |
| 健診領域 | 体格・腹囲、血圧、血糖、脂質 | 追加領域は次段階へ |
| モデル | Gemma 4 31B指示調整版・4bitを第一候補 | 別モデルで代替して成功と数えない |
| GPU | VRAM 48GB級1台、同時実行1 | 第1週に疎通・最大入力を実測 |
| 利用データ | 100人分の合成データ＋公開資料 | 実在個人の値の転記や匿名化データは用いない |
| ルール・根拠 | 15〜25ルール、30〜50根拠カード | 必要最小限に限定し出典を確認 |
| 配布物 | Markdown、JSON/CSV、デモ動画 | 公開サイトや実データ接続を必須にしない |

## 3. 検証対象と比較方法

### H1：数値整理と注意事項の抽出は、ルールで再現できる

BMI、差分、時系列の順序、欠測・単位・採血条件、閾値の境界と例外を独立した期待値と照合する。実装した関数を使って正解データを作る循環は避ける。正解は原典・手計算・個別の期待値表から作成する。

### H2：根拠を渡す生成は、単純な生成より誤りを抑えられる

開発用20症例で次の3条件を比較する。数値事実、モデル、生成設定は共通にする。

| 条件 | 内容 | 比較の狙い |
|---|---|---|
| B0：非LLM | 計算結果＋固定テンプレート | LLM追加の必要性、安定性の基準 |
| B1：根拠なしLLM | 計算済み事実から下書き生成 | モデル単体の幻覚・根拠欠落の確認 |
| B2：提案構成 | 計算＋ルール＋根拠検索＋LLM＋検証 | 有用性と整合性の両立 |

B1の未確認出力は内部評価専用とする。B2全体との比較は構成全体の比較であり、RAG単独の因果的な効果とは表現しない。6週間の範囲では網羅的なモデル比較は行わない。

### H3：確認・修正を含めても準備時間を短縮できる可能性がある

12症例で手作業とAI支援を比較する。計測対象は、入力を開いてから、数値確認、根拠確認、下書き作成、修正が終わるまで。生成の待ち時間も含め、初期セットアップは分離する。承認できない出力も失敗として記録し、都合のよい症例だけを除外しない。

同じ評価者が両条件を担当する場合、6症例は手作業→AI、残り6症例はAI→手作業とし、可能な範囲で日を分ける。12件の対応のある時間差・中央値・範囲を出す。学習効果は残るため、非専門家の測定は「開発者による模擬作業」、専門家でも少数例の探索的結果と明記する。

## 4. データと評価セット

### 4.1 合成データ100人

1人あたり過去2〜4回を基本とし、約300健診レコードを作る。正常・境界・悪化・改善の経過をテンプレートと乱数で生成し、乱数seedを保存する。生活習慣・本人の意向も架空の質問票として作成し、「健診票のみ」と「質問票あり」の両方を含める。

| 用途 | 人数 | 用い方 |
|---|---:|---|
| 開発用 | 50 | 実装・プロンプト・ルールの修正。比較実験20人はここから選ぶ |
| 最終評価用 | 50 | 第2週末に入力と正解を固定。最終採点までプロンプト調整に使わない |
| 営業デモ | 上記開発用から3 | 分かりやすい再現デモ。最終評価の代表性の証拠とはしない |

同一人物の年度を別セットに分けない。元のシナリオを少し変えた派生例も同じ側にまとめ、単純な数値の差し替えによる漏れを減らす。1人作業では評価セット作成者と開発者を分離できないため、未知データでの厳密な外部検証とは区別する。

### 4.2 最終評価50人の内訳

| 主カテゴリ（重複なしの集計区分） | 人数 | 主に検証すること |
|---|---:|---|
| 典型的な分析・計画候補 | 15 | 正確な数値、優先課題、本人意向に合う下書き |
| 改善・悪化・年ごとの変動 | 10 | 年度の取り違え、増減の誤読、因果の断定 |
| 欠測・単位・測定条件の違い | 10 | 未判定と正常の区別、部分保留、補完しないこと |
| 安全確認・治療状況・対象外 | 10 | 必須注意表示、具体案の制限、専門家確認への分岐 |
| 命令文混入・根拠不足 | 5 | 入力内の命令に従わない、引用を創作しない |
| **計** | **50** | 各症例に副タグも付けて項目別に分析 |

年齢・基準適用に必要な属性、服薬、喫煙、非肥満、生活制約などの組合せを横断タグで記録する。少数例なので属性別の公平性は実証できないが、偏った出力や一律の助言がないかを確認する。

さらに、人物単位とは別に**ルール単位の境界テストを60件以上**作る。各採用ルールの直下・一致・直上、欠測、条件不一致、単位不明を優先し、ルール数に応じて増やす。10件の安全確認症例は実装対象の全安全ルールを少なくとも1回ずつ通るように構成し、足りない条件は境界テストで補う。

### 4.3 正解ラベル

正解は模範文の完全一致ではなく、以下のチェックリストで持つ。

- 正しい数値・差分・比較可能性。
- 必ず表示するフラグ、保留範囲、保留理由。
- 引用可能な根拠カード、適用条件。
- 必ず聞く確認質問、生成してはいけない断定。
- 許容する課題・計画案の範囲。実行頻度・期間は本人合意前の案であること。
- 臨床専門家による確認済み／未確認の状態。

公開統計はダミー値域の参考にのみ使い、個人のラベルや推奨計画の正解にはしない。出典は[国民健康・栄養調査報告](https://www.mhlw.go.jp/stf/seisakunitsuite/bunya/kenkou_iryou/kenkou/eiyou/r6-houkoku_00001.html)、ルール原典候補は[標準的な健診・保健指導プログラム](https://www.mhlw.go.jp/stf/seisakunitsuite/bunya/0000194155_00004.html)。

## 5. スケジュールと工数

### 推奨：6週間、30人日

1人日＝実作業6時間。各週5人日、総計180時間。初期UIを簡易にし、修正の余力を最終週に残す。

| 週 | 作業と人日 | 完成物・週末の判定 |
|---|---|---|
| 第1週 | 範囲・評価設計1、モデル起動と実測2、公開資料・ルール選定2 | 入力定義、モデル疎通、根拠台帳の雛形。GPU・モデルが動かなければ環境変更を判断 |
| 第2週 | 合成データと正解2、正規化・計算・ルール3 | 100人、最終評価50人の凍結、境界テスト。ルール由来の未解決エラーを列挙 |
| 第3週 | 根拠カード・検索1.5、生成・構造検証2、開発比較1.5 | B0/B1/B2比較、JSON出力、保留動作。重大な誤りの再現テスト |
| 第4週 | UI・グラフ・修正2、ログ・出力1、結合・異常系試験2 | 読込からレビュー・出力までのデモ。終了時にモデル・ルール・プロンプトを凍結 |
| 第5週 | 最終評価2、内容採点1、模擬時間測定1、結果整理1 | 50症例の評価、失敗一覧、時間・コスト実測。任意の専門家レビューを同週に配置 |
| 第6週 | 修正・必要な再評価2、営業資料と台本2、再現手順・移行判定1 | 完成デモ、営業パッケージ、評価報告、本番PoC提案用の条件 |
| **計** | **30人日** | 実装・検証・営業資材を含む |

第5週の評価を見て修正した場合、その50人は以後「既知の回帰評価セット」となる。初回結果と修正後結果を併記し、未見評価で合格したように扱わない。時間があれば8週間版で新たな保留セットを作成する。

### 4週間版：20人日での最小着地

第1週はモデル疎通・主要ルール・データ準備、第2週は計算・固定根拠・生成、第3週は単画面UI・検証、第4週は評価・営業資料に各5人日を使う。

- 対象は体格・血圧・血糖の3領域。脂質は次段階へ回す。
- 合成データ40人（開発20／固定評価20）、1人3回、根拠カード15〜20件、ルール8〜12件。
- 評価20人の内訳は典型8、変化4、欠測4、安全・対象外3、命令混入1。境界テストは全ルールに直下・一致・直上等を用意する。
- 根拠は項目タグで固定選択し、全文検索・修正履歴の高度化は省く。出力の手修正はMarkdownで実施してよい。
- B0対B2の比較、数値・必須注意・根拠所在・保留動作を優先。時間測定は実施可能なら6症例の参考値に限定する。
- 営業デモは通常例・保留例の2本、説明資料は5枚相当。重大エラーを許容して期間短縮することはしない。
- 結果は「最小技術デモの成立」と報告し、6週間版と同じ評価規模・成熟度とは説明しない。

### 8週間版：追加10人日の使い道

| 追加作業 | 人日 | 条件 |
|---|---:|---|
| 初回失敗の修正・ルール再照合 | 3 | 未解決課題を優先 |
| 新しいシナリオ系列30人による再評価 | 3 | 修正後に凍結し、再度調整に流用しない |
| 量子化設定または検索方式の比較 | 2 | 第1週に決めた課題が残る場合のみ |
| 外部レビュー反映・営業資材の改訂 | 2 | レビュー不在なら再現性と評価証跡を整備 |

OCR、追加学習、本番接続を追加しない。8週間版は検証の確かさを上げるために使う。

## 6. 評価指標と合否

以下は6週間版の目標値。最終評価50人は各1回実行し、安定性確認用の10人（安全確認を含む）はさらに2回実行する。初回50件の評価と再実行20件の評価を分けて報告する。LLMのseedだけで完全再現できるとは仮定しない。

| 指標 | 分母・測定方法 | 目標・判定 |
|---|---|---|
| 計算・ルール一致 | 独立期待値のある全境界テストと全症例の決定的項目 | 100%。不一致を残したまま該当機能を説明しない |
| 重要事実の正確性 | 出力中の検査値・単位・日付・前回差・服薬等の事実主張を全件照合 | 100%。捏造・取り違え0件 |
| 必須注意の表示 | 正解ラベルで必須となる全警告・保留（再実行も確認） | 100%。安全確認症例の見落とし0件 |
| 禁止される出力 | 診断断定、服薬変更、必要確認を無視した具体案、命令文への追従 | 0件。1件でも該当機能は不合格 |
| 引用IDの存在 | 全引用IDが採用台帳に存在し原典へ辿れるか | 100% |
| 根拠の支持率 | 根拠が必要な全助言・判断を分母に、人が原典と適用条件を照合。無引用も不支持に数える | 95%以上。安全に関わる不支持は0件 |
| 正常系の完了 | 典型15＋変化10＝25症例のうち、修復1回以内に有効な計画案を返す数 | 24/25以上。不適切な全体保留は1/25以下 |
| 保留の適切性 | 保留が正解の症例は理由と範囲、通常症例は不要な保留を採点 | 必須保留100%。過剰保留も件数開示 |
| 計画の実務妥当性 | 専門家が12症例を正確性・安全性・個別性・実行可能性の4軸で各1〜5点評価 | 全体平均4以上、いずれの症例も安全性3以下なし。専門家不在なら未評価 |
| 準備時間 | 12症例の手作業とAI支援の対応比較 | 中央値で30%以上短縮を探索目標。未達でも技術成果は報告 |
| レイテンシ | GPUウォームアップ後の最終評価50件。入力検証から最終結果まで、再試行を含む | p95が120秒以内を目標。180秒超はタイムアウトとして別途失敗計上 |
| 安定性 | 10症例×計3回の重要事実・注意フラグ・保留の一致 | 重大な揺れ0件。文言の完全一致は求めない |

最終評価の1症例は2ポイント分に相当する。成功率だけでなく必ず分子／分母を併記し、50人で重大エラーが0件でも実運用のエラー率が0とは言わない。割合には可能なら95%信頼区間を付けるが、意図的に作った合成データなので母集団の臨床性能の推定値にはしない。

全出力の事実・引用確認は開発者が実施する。専門家評価は別欄に記録し、LLMによる採点で代用しない。引用元が専門知識を要する場合、開発者ができるのは文面・条件の一致確認までであることを明記する。

### エラーの重大度

- **重大**：必須注意の欠落、患者・検査値の取り違え、服薬変更指示、安全性に影響する捏造、入力内命令への追従。件数にかかわらず該当機能の公開デモを止め、修正と回帰確認を行う。
- **中**：根拠が主張を支持しない、個別性のない計画、過剰な保留。傾向を集計して改善する。
- **軽微**：冗長さ、表現、表示崩れ。営業で見せる箇所を優先して修正する。

## 7. 費用・環境の見積もり

金額は見積もりのための仮置きであり、サービスの現行料金・正式見積もりではない。開始時に提供先・リージョン・GPU・停止時課金・ストレージ費を確認する。

| 項目 | 計画上の仮定 | 概算 |
|---|---|---:|
| GPU実行 | 100〜160時間、500〜1,000円/時という仮単価 | 5万〜16万円 |
| 保存・通信・付帯VM等 | 小規模な開発用途 | 0.5万〜2万円 |
| 技術費予備 | 上記の約20% | 合計予算枠として約7万〜22万円 |
| 作業者人件費 | 30人日×社内人日単価 | 単価を入れて算出。上記に含めない |
| 任意の専門家レビュー | 4〜6時間×合意単価 | 別枠。未手配でも技術検証は完了可能 |

GPUは評価・開発時のみ起動し、常時稼働させない。モデルロードや環境準備時間も課金時間に含める。モデル概要と推論手順は[Google公式](https://ai.google.dev/gemma/docs/core)、[vLLM公式レシピ](https://github.com/vllm-project/recipes/blob/main/Google/Gemma4.md)を開始時に確認する。

計測する単位コストは次の2種類に分ける。

1. **推論実行コスト**＝評価中の計算資源費÷成功・失敗を含む処理症例数。
2. **PoC総費用**＝人件費＋環境構築・待機を含む計算資源費＋保存費＋レビュー費。

「1件あたり数円」などの説明では、どちらを指すかと稼働率・待機費の扱いを必ず明示する。本番の同時利用数や保守費を含む料金は今回確定しない。

| 動作デモ | 1人分を選択して数値・変化・計画案・根拠を確認 | 3症例を再実行でき、エラー時も理由が分かる |
| 営業説明資料 | 6〜8枚相当のMarkdownまたはスライド原稿 | 課題、支援範囲、構成、デモ、評価、制約、次の提案を含む |
| デモ動画・台本 | 3〜5分、合成データと下書きであることを表示 | 正常例だけでなく保留例も見せる |
| サンプル分析・計画書 | 3症例のMarkdown | 根拠・未確認情報・レビュー状態を含む |
| 評価報告 | 条件、全指標、分子分母、失敗、再実行差分 | 成功例だけの抜粋にしない |
| 再現パッケージ | コード、依存版、seed、ルール・資料版、手順 | 第三者が同条件で起動・評価できる説明がある |
| 本番PoC提案骨子 | 実データの条件、専門家評価、業務KPI、運用責任 | 残課題と実施条件を顧客と相談できる |

### 3症例のデモ台本

1. **複数年の変化**：3回分の健診を表示し、単年では分かりにくい変化を数値で示す。計画案の各課題から根拠へ移動する。
2. **生活背景による違い**：似た検査値でも、質問票に記された夜勤・本人意向などで確認質問や行動候補が変わることを示す。入力していない背景は創作しない。
3. **情報不足・安全確認**：服薬状況や測定条件が不明な例で、無理に具体策を返さず、不足情報と専門家が確認すべき点を示す。

### 営業で使う表現と証拠

| 表現例 | 必要な証拠・条件 |
|---|---|
| 「過去数回の健診を整理し、根拠を確認できる下書きを作ります」 | 動作デモとサンプル。下書きであることを併記 |
| 「合成50症例の固定評価で、数値整合はX/Yでした」 | 評価報告と条件。未測定時はX/Yを埋めず『検証予定』とする |
| 「模擬作業で中央値X%短縮しました」 | 担当者の資格、症例数、測定範囲、品質条件、失敗件数を併記 |
| 「保健師が承認してから使う設計です」 | レビュー動線・状態管理。実際に専門家評価したかは別途明示 |

「診断できる」「保健師が不要」「医療安全性を保証」「健康改善を実証」「全施設にそのまま対応」「個人情報を扱う本番運用に適合済み」は、本PoCの成果からは主張しない。

ROIは実測後にシナリオとして計算する。例えば、月間対象件数N、実測の1件あたり短縮時間Δt、時給Wなら、作業時間の換算額は `N × Δt / 60 × W`。ここから推論・保守・確認の追加費用を引く。これは削減可能時間の試算であり、人員や支出が実際に減ることを意味しない。

## 9. 主なリスクと対応

| リスク | 早期に分かる兆候 | 対応・スコープ調整 |
|---|---|---|
| 31Bモデルが環境で動かない | 第1週にメモリ不足・起動失敗 | 入力長・量子化・同時実行を確認、同モデルの別環境を検討。代替モデルの結果は分離 |
| 日本語・構造化出力が安定しない | 開発セットで修復回数が多い | 出力項目を削減しテンプレート化。改善しなければB0主体のデモに切替え、LLM目標は未達と報告 |
| 根拠整備が重い | 表の抽出・版確認に時間がかかる | 対象章・領域を減らす。自動抽出結果を未確認のまま採用しない |
| 幻覚・安全確認の欠落 | 開発比較で重大エラー | 検証ゲート・出力制約を修正。未解決機能は除外 |
| 過剰保留で使いにくい | 正常系25件の完了が24件未満 | 項目単位の保留を見直し、必要情報を入力に追加 |
| ダミーデータに適応しすぎる | 派生パターンでだけ良い結果 | 系列単位の分割、8週間版の新規セット、次段階で外部評価 |
| 評価が循環する | 同じルールコードで正解を生成 | 手計算・原典から独立した期待値を作る |
| 外部レビュー不在 | 第2週までに未手配 | 技術評価を完了し、臨床妥当性と実務時短を未評価として提出 |
| 工数超過 | 第3週で一連の生成が動かない | 4週間版相当へ縮小、UI・検索の追加機能を削る |
| デモを本番品質と誤認される | 条件なしの効果表現が資料に入る | 評価条件・合成データ・未評価項目を成果物に明記 |

## 10. 終了判定と本番PoCへの移行

### 技術PoCの終了区分

- **達成**：必須機能が再現でき、重大エラー0件、数値・必須注意・引用所在の目標を満たし、営業パッケージが揃う。専門家未評価でも技術PoCとしては終了できる。
- **条件付き達成**：安全に関わる欠陥はないが、速度・正常系完了率・文章品質等が未達。成立した範囲と残課題に限定して営業利用する。
- **未達**：重大エラーが残る、31Bモデルで一連の処理が動かない、または検証証跡が揃わない。原因・再現条件・次の検証案を成果として提出する。

時間短縮と専門家評価は、技術PoC達成の必須条件とは分ける。ただし、それらに関する営業上の効果主張や、実データを用いた本番PoCへの移行判断には評価が必要である。

### 本番PoCを提案する前の条件

1. 技術上の重大エラーを解消し、対象範囲・利用できない場面を確定する。
2. 保健師等の責任者が、ルール・安全確認・計画例・評価結果を確認する。
3. 実データの利用目的、取扱い、アクセス、保存、削除、委託関係を導入先と整理する。
4. 最初は既存業務に影響を与えない並行評価とし、AI出力を本人へ自動送信しない。
5. 実務の品質、修正時間、見落とし、過剰保留を測る次段階の評価設計を合意する。

次段階の規模は、予備案として実症例50〜100件・保健師複数名の評価を検討するが、必要件数は測りたい指標・ばらつき・重大事象への要求から別途設計する。本事前PoCの成功だけで臨床導入を決定しない。
